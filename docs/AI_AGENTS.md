# AI агенти в проекта

Този документ описва как AI беше използван при изграждането на AI Tools Hub, как да настроите AI агент за продължаване на разработката и кои начални промптове да използвате.

## 1. Какво е AI агент за разработка

AI агентът е модел (например Claude), който освен да отговаря на въпроси, **сам изпълнява стъпки** в проекта: чете файлове, пише код, пуска команди и тестове и поправя грешките, които вижда. Разликата спрямо обикновен чат е, че агентът работи директно с кода и проверява резултата си.

| Агент | Къде работи | Подходящ за |
|---|---|---|
| **Claude Code** | Терминал / VS Code / уеб | Многостъпкови задачи: нов модул (миграция + API + UI + тестове), рефакторинг, дебъгване |
| **Cursor** (Agent mode) | Редактор, базиран на VS Code | Промени в няколко файла с преглед ред по ред |
| **GitHub Copilot** | VS Code | Довършване на код в движение, малки функции |
| **v0 / Lovable** | Браузър | Бърз прототип на UI екран, който после се пренася в проекта |

## 2. Как AI помогна по дни

| Ден | Задача | Как беше използван AI |
|---|---|---|
| 6 | Вход, роли, табло | Ръководство стъпка по стъпка (`docs/Ден6_…docx`), обяснение на Sanctum, CSRF и CORS |
| 7 | AI инструменти (CRUD) | Структура на таблиците и връзките, валидация, качване на снимки, форма с всички полета |
| 8 | UI и UX | Цветова схема (индиго + slate, контраст AA), layout на страниците, мобилно меню, модални прозорци, toast съобщения |
| 9 | Сигурност и админ панел | Реализация на TOTP (2FA) по RFC 6238, middleware за роли, стратегия за кеширане, одит лог |
| 10 | Документация и почистване | README, този документ, `CLAUDE.md`, поправка на `start.sh`, премахване на излишни файлове, тестове |

Принципи, които работят добре:
- **Даваме контекст, не само задача.** `CLAUDE.md` описва стека и правилата, така агентът не „изобретява“ нова структура.
- **Малки стъпки с проверка.** След всяка стъпка: `php artisan test`, отваряне в браузъра.
- **Агентът пише тестове заедно с кода.** Тестовете са доказателството, че работи.
- **Преглеждаме кода преди commit.** AI може да сгреши, а ние носим отговорност за резултата.

## 3. Настройка на агент за разработка

1. Клонирайте проекта и го стартирайте (`./start.sh`), за да може агентът да пуска тестове.
2. **Claude Code:** в папката на проекта изпълнете `claude`. `CLAUDE.md` се зарежда автоматично.
3. **Cursor / Copilot:** добавете `CLAUDE.md` в контекста (в Cursor: `@CLAUDE.md`, или го копирайте в `.cursorrules`).
4. Започнете с един от промптовете по-долу.

## 4. Начални промптове

Копирайте промпта и сменете частите в `[скоби]`.

### 4.1. Запознаване с проекта (винаги първо)
```
Прочети CLAUDE.md и README.md. Разгледай структурата на backend/app и frontend/src.
Пусни `docker compose exec php_fpm php artisan test` и ми кажи дали всички тестове минават.
Обобщи в 5-6 точки как работят ролите, одобрението на инструменти и 2FA.
Не променяй нищо, само докладвай.
```

### 4.2. Нова функционалност (пълен цикъл)
```
Добави [любими инструменти: потребителят може да маркира инструмент със звезда
и да вижда списък „Любими“ в профила си].

Следвай правилата от CLAUDE.md:
1. Миграция + модел + връзки.
2. Endpoint-и в routes/api.php, защитени с auth:sanctum; запис в одит лога чрез ActivityLogger.
3. Feature тестове в backend/tests/Feature - пусни ги и поправи, докато минат.
4. Frontend: типове в lib/types.ts, заявки с apiJson, toast след успех, мобилен изглед.
5. Добави новите endpoint-и в таблицата „API“ в README.md.
Преди да пишеш код, ми покажи кратък план и изчакай одобрение.
```

### 4.3. Поправка на бъг
```
Бъг: [при филтър по категория + търсене списъкът показва и неодобрени инструменти].
Стъпки за възпроизвеждане: [влез като qa@example.com, отвори /tools, избери категория...].
1. Намери причината (покажи файла и реда).
2. Напиши тест, който пада заради бъга.
3. Поправи кода, така че тестът да минава, без да чупиш останалите.
```

### 4.4. Нова роля
```
Добави роля „[data-analyst]“ с етикет „[Data Analyst]“.
Обнови User::ROLES, RoleSeeder, DatabaseSeeder::TEST_USERS (тестов акаунт),
ROLE_LABELS и ROLE_INTRO във frontend/src/lib/roles.ts.
Провери, че админ панелът позволява избор на новата роля, и пусни тестовете.
```

### 4.5. Нова секция в админ панела
```
В админ панела (frontend/src/app/admin/page.tsx) добави таб „[Статистики]“ с
[брой инструменти по категория и по роля, топ 5 по рейтинг].
Данните да идват от нов endpoint GET /api/admin/stats, защитен с role:owner
и кеширан в Redis за 10 минути (изчиства се като tools.stats). Добави тест.
```

### 4.6. Преглед на сигурността
```
Направи преглед на сигурността на backend-а:
- маршрути без нужната защита (auth, role, policy);
- mass assignment (fillable), валидация на всички входни данни;
- изтичане на чувствителни полета в JSON (пароли, 2FA ключове);
- rate limiting на вход, 2FA и коментари.
Върни списък: проблем → файл → риск → предложена поправка. Не променяй код без потвърждение.
```

### 4.7. Достъпност и мобилен изглед
```
Прегледай страниците в frontend/src/app за достъпност (WCAG AA) и мобилен изглед (ширина 375px):
етикети на полетата, контраст, фокус с клавиатура, aria атрибути на модалните прозорци и табовете,
хоризонтален скрол. Поправи откритото и опиши промените.
```

### 4.8. Подготовка за production
```
Подготви проекта за production deploy:
- отделен docker-compose.prod.yml (next build + next start, APP_DEBUG=false, config:cache);
- инструкции за HTTPS и SANCTUM_STATEFUL_DOMAINS за реален домейн;
- раздел „Deploy“ в README.md.
```

## 5. Добри практики при работа с агент

- Една задача на промпт. Големите задачи се разделят на стъпки (4.2 изисква план първо).
- Винаги искайте тестове и пускане на тестовете.
- Преглеждайте промените с `git diff`, преди да ги commit-нете.
- Не давайте на агента реални пароли или API ключове. Използвайте тестовите акаунти.
- Когато агентът сбърка, обяснете **какво** е грешно и **как** да се провери. Така поправката е по-точна.
